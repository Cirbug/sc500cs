Confirmed frame-buffer ownership defect
---------------------------------------
video_in alternates two write banks at each input frame start. video_out
latches the published bank at its own frame start. No active-reader bank
is returned to video_in, so the writer can overwrite the displayed bank.

Reproduce using preserved baseline video_in and a small synchronous FIFO model:
E:/iverilog/bin/iverilog.exe -g2012 -I user_source/hdl_source -s tb_video_buffer_ownership -o D:/2026fpga/bank/rgb_stream_fix_20261017/ownership.vvp D:/2026fpga/bank/video_safe_20261017/tests/tb_video_buffer_ownership_legacy.sv D:/2026fpga/bank/video_safe_20261017/tests/video_in_legacy.v
E:/iverilog/bin/vvp.exe D:/2026fpga/bank/rgb_stream_fix_20261017/ownership.vvp
Observed:
REPRODUCED buffer ownership violation: camera_frame=3 write_bank=0 HDMI_active_bank=0 address=0 writes=1441

This diagnostic models the display's once-per-refresh bank latch, with
equal frame periods and different phase. It proves missing bank ownership,
not the exact phase/extent of corruption on this board. It is intentionally
a reproduction test, not an acceptance PASS. No production RTL was edited.

Other inspection findings
-------------------------
Top-level video_in.I_mipi_rx_error is tied to zero.
Input FIFO full_flag is disconnected; display empty_flag is not used to
invalidate a frame. Current MIPI FPS counts frame-start events and cannot
certify 1944 complete RAW lines or error-free payloads.
No configured display split corresponding to the photo was identified.

Required fix/acceptance scope
-----------------------------
Use explicit active-reader ownership and publish only complete frames.
If using a third live bank, account for SD snapshot allocation: existing
SD base=8000000 address units overlaps a third bank starting at 6400000.
Do not add a third bank without moving/validating that allocation.
Also instrument CSI line length/count, receiver errors, input overflow and
display underflow to distinguish upstream corruption from buffer tearing.
Re-run ownership, pixel payload, SD arbitration, timing/resource checks,
then verify the physical image. A 30 fps counter alone is not acceptance.
