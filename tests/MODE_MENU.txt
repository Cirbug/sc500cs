========================================================================
菜单重排 + 色度 7 位扩容 / 2026-10-26
========================================================================

背景：现场反馈两条 —— ① 色度滑条"不顺滑"；② 菜单分页越来越乱
（同一类参数散在不同页、页头与行名重名、有的页只剩 2 行、有的页塞满 8 行）。

一、色度为什么"不顺滑"（两个独立原因，都修了）

  1. 脏键漏项（主因）。mcu_menu.h 的 mcu_menu_poll() 用 key[7] 判断是否需要
     重绘，原来 key[3] 只放 picture|gamma —— 改色度时键不变，poll 提前返回，
     菜单根本不重绘；曝光/增益在 key[1]/key[2] 里所以顺滑。
     修法：key[3] 并入 lsc_strength(7 位) 与 track_color(2 位)。
  2. 档位太粗。0xec 原本 5 位、0..31，而滑条有 127 个手指位置 -> 每档要滑
     4 像素。曝光有 3988 档所以每像素都在变。
     修法：扩到 7 位（见二）。

二、色度 7 位扩容（APB 0xec）

  硬件：lens_shading_correction.v 的 I_strength[6:0]、缩放 prod[12:6]（÷64）；
        mcu_ui_apb_regs.v 的 O_lsc_ctrl[6:0]、0xec 写 I_pwdata[6:0]、复位 7'd56。
        语义：0 = 完全旁路，64 = 编译期表值原样（等价旧 16），127 = 约 194%。
        位宽：mag ≤ 20，20*127 = 2540 < 8192（13 位 prod），未增资源。
  固件：LSC_STRENGTH_DEFAULT 14u -> 56u（画面观感不变），滑条 *hi=127。
  兼容：新增只读能力字 0xf8 = "LSC2"（放在原 COL1 那把已停用的地址上，
        0xf4 留给以后的目标色/使能寄存器）。固件探测 0xf8：有则写 7 位，
        只有 0xf0「LSC1」的老 bit 则按 4:1 折算后写 5 位，同一档位观感一致。
  效果：128 档 ÷ 127 个滑条位置 ≈ 1:1，手感与"增益"一致；现场常用区间
        （旧 12~18）变成 48~72，分辨率提升 4 倍。

三、重排后的菜单（每页 ≤ 8 行，渲染器硬上限）

  相机设置  图像调整 / 曝光控制 / 显示模式 / 目标追踪 / 拍照录制 / 系统信息   (6)
  图像调整  黑电平 / 伽马 / 饱和度 / 白平衡 / 降噪 / 色度 / 恢复默认 /(直方图) (7~8)
  曝光控制  曝光 / 增益 / 帧长 / 数字亮度 / 自动曝光                        (5)
  显示模式  普通画面 / 图形识别 / 运动检测 / 图像特效                        (4)
  目标追踪  目标跟踪(开/关) / 目标色(红·蓝·绿) / 重新识别 / 自动对焦         (4)
  拍照录制  单张拍照 / 开始录制 / 停止录制 / 保存间隔 / 已保存 / 状态         (6)
  系统信息  标志 / 统计信息                                                  (2)

  逐条：数字亮度 图像页 -> 曝光页；色度 系统页 -> 图像页；恢复默认仍在第 7 行
  （它后面是能力相关的直方图行，条件行必须留在最后，索引才稳定）；曝光页第 5 行
  由与页头重名的"曝光控制"改名"自动曝光"；显示模式页去掉三色三行；目标追踪页
  改成"开关 + 一行选色"；录制页去掉只有它才有的"返回"行。

四、三色跟踪为什么可以只占一行（"解耦"的含义）

  重排前 image_step 的 5/6/7 同时表达"跟踪中"和"跟哪个颜色"，所以显示模式页
  必须列三行。重排后由目标追踪页的开关决定跟踪与否、由"目标色"决定颜色 ——
  用户看到的是两个独立项，一行选色即可。
  本版（方案甲）内部仍写 image_step = 5/6/7（5=红 6=蓝 7=绿），由 menu_input.h
  的 track_apply()/track_sync_from_step() 双向映射，所以：
    · 不需要新增持久化字段（image_step 已在 image_ctrl 里存了）；
    · OSD 的"追踪红色/蓝色/绿色"标签（cn_track_id，按 image_step-5 取字）不受影响；
    · 不动任何 HDL 使能逻辑。
  代价：跟踪开着时显示模式页没有行高亮（5/6/7 不在它的 4 个模式里），跟踪状态
  由目标追踪页与画面上的跟踪框表达。

五、标签的单一来源（重要，别再手改 manifest）

  tools/generate_menu_font.py 顶部的 LABELS / PANEL_LABELS / PANEL_VALUES 才是
  标签源；它生成 ui_font_cn.v(ROM)、ui_font_cn_map.vh(RTL 的 cn_label_id 等)、
  labels.hex/rows.hex(测试夹具)，并**反过来写出** assets/menu_font/manifest.json；
  tools/generate_mcu_menu_map.py 再据 manifest 生成 FDwork/shared/mcu_menu_map.h。
  所以改菜单顺序必须改生成器列表、再依次重跑两个生成器（Pillow 用内置 Python）。
  --extend-existing 会从已有 rows.hex 复用字形位图并保持字符 ID 顺序，
  因此本次 ui_font_cn.v 逐字节未变，只重排了 ID 映射。

六、兼容性等价测试的一处放宽（已知取舍）

  tests/tb_mcu_menu.sv 原本要求"MCU 生成的表格与 RTL 自带 legacy 菜单逐像素一致"。
  RTL 那份固定布局（ui_osd.v 的 legacy 分支）里的**行几何与取值是硬编码的**，
  没有跟着重排走；而生产环境 design_top_wrapper 恒为 MCU_MENU(1)，那份布局只是
  兼容回退，改它没有产品价值。因此该 TB 对画面页/录制页（mode 1/2/6/7）不再做
  逐像素比对（表格写入、busy、提交状态等协议检查对全部 9 个模式仍然生效，
  标签同步仍由生成器保证）。其余页面照旧逐像素比对。
